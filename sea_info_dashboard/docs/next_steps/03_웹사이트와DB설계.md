# 03. 웹사이트 구성과 DB 확장 설계

## 1. 현재 구조를 유지하는 이유

현재 FastAPI가 정적 화면과 API를 함께 제공하므로 브라우저는 같은 서버의 `/api/...`를 호출한다. 첫 완성본에서는 이 구조를 유지하면 배포와 학습 범위를 줄일 수 있다. React·Next.js 도입은 화면 상태가 복잡해질 때 다시 판단한다.

```text
브라우저: HTML / CSS / JavaScript
    ↓ fetch('/api/...')
FastAPI main.py → models.py 요청·응답 검증
    ├─ services.py → 해양 데이터 제공자
    ├─ species_service.py → WoRMS
    ├─ image_service.py → 이미지 처리·AI·학명 대조
    └─ database.py → SQLite
```

## 2. 화면별 다음 작업

| 화면 | 현재 흐름 | 다음 작업·완료 기준 |
|---|---|---|
| 대시보드 | 지역·날짜·요약 카드 | 각 카드에 출처·자료 시각·상태 표시 확인 |
| 물때·예보 | 일일 사건 목록·파고 차트·관측 | 첫 만조와 지금 이후 다음 만조를 구분; 데이터 없으면 이유 표시 |
| 생물 검색 | 목록·상세 | 국명과 학명, 동의어와 인정 학명 구분 |
| 사진 분석 | 업로드·동의·분석 결과 | 처리 중 중복 클릭 방지, 후보·한계·출처 확인 |
| 관찰 기록 | 생성·조회·수정·삭제 | 분석 결과를 선택해서 기록과 연결 |
| 조회 이력 | 목록·당시 결과·사진 | 보관 기한 안내, 단건 삭제와 사진 삭제 기능 추가 |
| 해조류 성분 카드 | 신규 제안 | 식품 상태·기준량·단위·출처 포함한 5개 카드 |
| 자료 기반 Q&A | 신규 제안 | 답변 문장과 실제 검색 근거 연결 |

모바일에서는 지역·날짜 → 요약 → 세부 자료 → 생물 인식 → 기록 순으로 배치한다. 360px 안팎 화면에서 가로 스크롤, 버튼 겹침, 긴 학명 잘림을 점검한다. 대기·빈 결과·일부 실패·완전 실패를 각각 확인한다.

## 3. 기존 API와 신규 API 구분

기존 경로는 `/api/status`, `/api/regions`, `/api/dashboard`, `/api/species`, `/api/species/{aphia_id}`, `/api/analyze`, `/api/records`, `/api/records/{id}`, `/api/history`, `/api/history/{id}`, `/api/history/{id}/image`이다. 메서드와 입력 모델은 실행 중 `/docs`에서 확인한다.

아래는 **구현 전 제안**이다. 한 기능씩 모델 → DB → 경로 → 화면 순서로 만든다.

| 제안 경로 | 역할 | 먼저 정할 규칙 |
|---|---|---|
| `DELETE /api/history/{id}` | 이력·연결된 분석용 사진 삭제 | 관찰 기록의 연결이 있을 때 처리 |
| `GET /api/nutrients?food_id=...` | 식품별 성분 카드 | 제공기관 ID·단위·자료 버전 |
| `GET /api/sources/{id}` | 근거 문서 메타데이터 | 원문 URL·문서 버전·페이지 |
| `POST /api/chat` | 문서 근거 기반 답변 | 질문 길이·시간 제한·근거 없음 응답 |

사진 분석은 기존처럼 `multipart/form-data`를 사용한다. JSON 요청과 혼동하지 않도록 `/docs`와 프런트의 `FormData`를 함께 확인한다.

## 4. DB의 현재와 제안

현재 `records`는 ID와 관찰 기록 JSON을, `history`는 조회 조건·결과 JSON·시각·상태·분석용 JPEG를 저장한다. 실제 스키마는 `database.py`에 있다. 지금부터 모든 테이블을 다시 만들 필요는 없다.

확장할 때의 후보:

| 대상 | 추가·분리할 정보 | 목적 |
|---|---|---|
| records | nullable `analysis_history_id` | 관찰과 분석 이력 연결 |
| species_aliases | 국명·학명·AphiaID·출처·검토일 | 이름 대응의 근거 관리 |
| food_items | 제공기관 식품 ID·상태·기준량·버전 | 식품과 생물 종을 분리 |
| nutrient_values | 식품 ID·성분명·값·단위·출처 | 단위가 다른 값을 구분 |
| sources | 제목·기관·URL·발행일·확인일·이용 조건 | RAG와 카드의 근거 추적 |
| document_chunks | source ID·페이지·본문·버전 | 검색 결과를 원문으로 연결 |

각 변경은 기존 DB 백업 → 스키마 변경 → 기존 자료 변환 → 앱 재실행 → 조회·수정 검증 순서로 수행한다. 초기화 함수만 수정해도 기존 테이블에 새 컬럼이 생기는 것은 아니다. 첫 변경부터 SQL 마이그레이션 파일과 적용 이력을 남긴다.

## 5. 백업 경험을 서비스 강점으로 연결

현재 DB는 WAL 모드를 사용한다. 실행 중인 DB 파일 하나를 단순 복사하는 방식 대신 Python `sqlite3.Connection.backup()`을 이용한 백업 작업을 제안한다. 또는 서버와 연결을 완전히 종료한 뒤 복사한다.

백업 완료 기준은 파일 생성이 아니라 **복원 확인**이다. 별도 테스트 경로에서 `SEA_INFO_DB_PATH`를 복원본으로 지정해 기록 수, 대표 기록 내용, 분석 사진 열기를 확인한다. 원본 DB를 덮어쓰지 않는다. 백업에는 사진·메모가 포함되므로 보관 기간과 삭제 범위도 정한다.

## 6. 배포로 넘어가는 조건

첫 시연은 로컬 서버로 진행한다. 인터넷 공개 시에는 다음이 추가 작업이다.

1. 운영 환경 변수에 키를 설정하고 프런트 코드·로그에서 키가 보이지 않는지 확인한다.
2. HTTPS, 접근 제어, 업로드 제한, 사진 분석 호출량·비용 제한을 적용한다.
3. 사용자가 여러 명이면 기록·이력을 사용자별로 분리하고 서버에서 소유권을 검사한다.
4. DB가 재배포 후에도 남는 저장소를 사용한다. SQLite는 우선 단일 인스턴스·영속 디스크로 운영하고 확장 시 PostgreSQL을 검토한다.
5. 운영 서버는 개발용 `--reload`를 제거하고, 오류 로그·외부 API 상태·백업·복원을 확인한다.
6. 사진 전송·저장·삭제 정책과 데이터 출처 표시를 화면에 반영한다.

호스팅 업체는 이 조건과 예산을 정한 뒤 선정한다. 배포 성공 화면만으로 기록 영속성·접근 제어·외부 API 정상 연결이 검증되는 것은 아니다.
