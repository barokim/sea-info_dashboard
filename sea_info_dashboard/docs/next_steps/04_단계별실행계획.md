# 04. 단계별 실행 계획과 체크리스트

주당 6~10시간 정도를 가정한 6주 예시다. 학습 속도와 API 승인 일정에 맞춰 조정한다. 1~4주를 첫 완성본, 5~6주를 확장 실습으로 본다.

## 1주차 — 코드를 이해하고 기준 상태 기록

- [ ] 실제 앱 `main.py`와 가상환경의 라이브러리 파일을 구분한다.
- [ ] 기존 README의 실행 절차로 로컬 화면과 `/docs`를 연다.
- [ ] 기록 생성·조회·수정·삭제를 화면과 `/docs` 양쪽에서 실행한다.
- [ ] `models.py → main.py → database.py` 흐름을 직접 설명한다.
- [ ] 기존 테스트를 실행하고 결과를 기록한다.
- [ ] 국립해양조사원 두 API 활용신청을 진행한다.

```powershell
Set-Location C:\KBR\sea_info_dashboard
.\.venv\Scripts\python.exe -m unittest -v
```

산출물: 실행 방법과 현재 성공·실패 상태를 적은 작업일지. 완료 기준: 서버 재시작 후 본인이 만든 기록이 남고, PATCH와 DELETE 차이를 설명할 수 있다.

## 2주차 — API 실제 연결 확인

- [ ] WoRMS에서 국명과 학명을 각각 검색하고 같은 종의 상세를 확인한다.
- [ ] Open-Meteo의 날짜·좌표·시간대·변수 단위를 확인한다.
- [ ] 승인된 KHOA 키를 설정하고 인천 오늘 자료를 호출한다.
- [ ] 공식 응답과 화면의 시각·단위·지점을 비교한다.
- [ ] 키 없음·자료 없음·시간 초과·부분 실패 상태를 확인한다.
- [ ] 키를 제거한 응답 표본과 확인 결과를 남긴다.

산출물: 제공자별 검증표. 완료 기준: “키 설정됨”과 “실제 자료 수신 성공”을 구분하고 인천의 물때·관측값이 올바른 출처로 표시된다. 승인 대기 중에는 공개 API·화면 작업을 진행한다.

## 3주차 — 사진 분석과 기록 연결

- [ ] 기존 사진 검증·변환·동의 흐름을 이해한다.
- [ ] 로컬에서 실제 AI 키와 이미지 지원 모델을 설정한다.
- [ ] 사용 권한이 있는 소수 사진으로 유료 실호출을 확인한다.
- [ ] 선명한 사진·흐린 사진·여러 생물 사진·비생물 사진을 비교한다.
- [ ] 분석 이력과 관찰 기록을 연결하는 작은 DB 변경을 구현한다.
- [ ] 분석 실패·DB 학명 미등록·종 후보 불확실 상태를 표시한다.

산출물: 사례별 평가표와 관찰 기록 연결 기능. 완료 기준: 분석 결과에서 기록을 만들고, 나중에 당시 사진과 후보를 다시 볼 수 있다. 학명 일치만으로 사진 식별 성공을 판정하지 않는다.

실제 모델·키 설정 방법은 구현 시 공식 문서와 계정 사용 가능 범위를 확인한다. 기존 `.env.example`의 모델 값은 현재 프로젝트 설정 예시로 취급한다.

## 4주차 — 웹 완성도와 복원 가능한 시연

- [ ] 모바일 폭, 긴 학명, 키보드 조작, 오류 메시지를 점검한다.
- [ ] 출처·자료 시각·단위가 화면에서 확인되는지 점검한다.
- [ ] 이력 삭제의 DB·사진·기록 연결 규칙을 정하고 구현한다.
- [ ] 백업본을 별도 경로에 복원해 기록과 사진을 확인한다.
- [ ] 외부 API가 하나 실패해도 남은 시연 흐름을 진행한다.
- [ ] 공개 배포 여부를 정하고, 공개 시 인증·비용 제한·영속 저장을 먼저 적용한다.

산출물: 3~5분 시연 시나리오, 화면 캡처, 복원 확인 기록. 완료 기준: 지역 조회 → 생물 검색 → 사진 후보 확인 → 관찰 저장 → 재열기 흐름을 끝까지 수행한다.

## 5주차 — 전공 기반 해조류 정보 카드

- [ ] 김 관련 공식 식품 데이터와 공개 연구자료를 선정한다.
- [ ] 식품 상태·종·처리 조건·단위·출처 필드를 정한다.
- [ ] 검토한 카드 5개를 DB와 화면에 표시한다.
- [ ] 자료가 없는 항목을 비워 두고 비교 불가능한 조건을 설명한다.

산출물: 출처 있는 성분 카드. 완료 기준: 사용자 질문 하나에 어떤 자료와 기준으로 답했는지 설명할 수 있다.

## 6주차 — RAG와 에이전트 실습

- [ ] 검토 가능한 공개 문서 10개 안팎을 수집한다.
- [ ] 문서 검색만 먼저 만들고 관련 문단이 검색되는지 평가한다.
- [ ] 검색 결과를 사용한 답변과 원문·페이지를 함께 표시한다.
- [ ] 질문을 API 조회·문서 검색으로 나누는 라우터를 만든다.
- [ ] 고정 질문 목록으로 답변·근거·실패 처리·비용을 비교한다.

산출물: 근거 기반 Q&A와 역할 분리 흐름. 완료 기준: 근거가 없는 질문에는 모른다고 답하고, 단순 함수 호출 대비 역할 분리의 효과를 설명한다.

## 작업 한 건을 끝내는 방식

1. 사용자 행동과 기대 결과를 한 문장으로 적는다.
2. 해당 모델·서비스·DB·화면만 작게 수정한다.
3. 기능에 맞는 검증을 수행한다. API 파싱·DB 변경은 회귀 테스트, 화면 배치는 브라우저 확인을 중심으로 한다.
4. 결과와 남은 문제를 적고 다음 작업으로 넘어간다.

작업일지 양식:

```text
날짜:
목표 / 수정한 파일:
검증 조건: 지역·날짜·데이터 출처·실호출 또는 모의 응답
기대한 결과 / 실제 결과:
통과 여부 / 남은 문제 / 다음 행동:
```
